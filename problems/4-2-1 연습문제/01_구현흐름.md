## 문제 1. 검색 도구와 대화 메모리를 갖는 Agent

### 문제

정책 문서를 검색하여 답하는 고객 상담 Agent의 처리 흐름이다. 빈칸 A~E에 들어갈 처리 블록을 순서에 맞게 작성하라.

`정책 Document 목록 → (A) → split_docs → (B) → vectorstore → (C) → search_policy 도구 → (D) → Agent → (E) → 최종 AIMessage`

### 요구사항

- 문서는 300자 단위, 50자 중첩으로 분할한다.
- 검색기는 유사한 청크 3개를 반환한다.
- `search_policy(query: str) -> str`는 검색 결과의 `page_content`를 줄바꿈으로 결합한다.
- Agent는 같은 `thread_id`에서 이전 대화를 기억해야 한다.
- 각 빈칸에 주요 클래스·함수와 핵심 인자를 함께 적는다.

## 정답 1

### 정답 코드

```python
# A
splitter = RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=50)
split_docs = splitter.split_documents(policy_documents)

# B
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",
    api_key=os.environ["GMS_KEY"],
    base_url="https://gms.ssafy.io/gmsapi/api.openai.com/v1/",
)
vectorstore = Chroma.from_documents(split_docs, embeddings)

# C
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

@tool
def search_policy(query: str) -> str:
    """고객 서비스 정책을 검색합니다."""
    docs = retriever.invoke(query)
    return "\n".join(doc.page_content for doc in docs)

# D
agent = create_agent(
    model=llm,
    tools=[search_policy],
    system_prompt="정책 질문은 도구로 검색한 근거에 따라 답하세요.",
    checkpointer=MemorySaver(),
)

# E
config = {"configurable": {"thread_id": "customer-1"}}
result = agent.invoke(
    {"messages": [("user", "환불 정책을 알려줘")]},
    config=config,
)
print(result["messages"][-1].content)
```

### 핵심 해설

- A는 `Document 목록 → 청크 목록`, B는 `청크 → 임베딩 벡터 → Chroma`, C는 `질문 → 관련 Document 목록`을 담당한다.
- `@tool`은 함수 이름, docstring, 타입 힌트로 LLM이 읽을 도구 명세를 만든다. 검색 결과는 문자열로 바뀌어 Agent에 돌아간다.
- `create_agent`가 모델·도구·시스템 프롬프트·체크포인터를 결합한다. `MemorySaver`는 `thread_id`별 상태를 저장한다.
- 검색 개수를 바꾸려면 C의 `k`, 문맥 분할을 바꾸려면 A의 두 인자, 기억 범위를 나누려면 E의 `thread_id`를 수정한다.

## 문제 2. StateGraph Direct와 ReAct 실행 경로

### 문제

아래 두 그래프의 공통 흐름과 서로 다른 마지막 연결을 완성하라.

- 도구가 불필요한 경우: `START → (A) → END`
- 도구가 필요한 Direct: `START → (A) → (B) → END`
- 도구가 필요한 ReAct: `START → (A) → (B) → (A) → ... → END`

### 요구사항

- 상태는 `MessagesState`를 사용한다.
- A는 도구가 바인딩된 LLM을 호출하고 `{"messages": [response]}`를 반환한다.
- A의 마지막 메시지에 `tool_calls`가 있으면 B로, 없으면 `END`로 이동한다.
- B는 `ToolNode(tools)`이다.
- Direct와 ReAct에서 달라지는 엣지를 명시한다.

## 정답 2

### 정답 코드

```python
def call_model(state):
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state):
    return "tools" if state["messages"][-1].tool_calls else END

# A = agent 노드, B = tools 노드
graph = StateGraph(MessagesState)
graph.add_node("agent", call_model)
graph.add_node("tools", ToolNode(tools))
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue)

# Direct일 때
graph.add_edge("tools", END)

# ReAct일 때는 위 한 줄 대신 다음을 사용한다.
# graph.add_edge("tools", "agent")

app = graph.compile()
```

### 핵심 해설

- A는 `messages` 상태를 받아 `AIMessage` 하나를 리스트로 반환한다. `MessagesState`의 reducer가 이를 기존 메시지에 누적한다.
- `AIMessage.tool_calls`에는 도구 이름과 `args` 딕셔너리가 들어 있다. B는 이를 실행해 `ToolMessage`를 상태에 추가한다.
- Direct는 도구 결과를 낸 직후 끝나므로 자연어 최종 답변을 다시 만들지 않는다. ReAct는 도구 결과를 A에 돌려보내 LLM이 관찰하고 다음 행동 또는 최종 답변을 결정한다.
- 도구 결과를 최종 자연어 답변으로 바꿔야 하면 `tools → agent`, 한 번의 도구 실행 결과 자체가 출력이면 `tools → END`를 선택한다.

## 문제 3. Agent 회귀 평가 흐름

### 문제

환불 상담 Agent의 정확도를 자동 평가하는 파이프라인을 완성하라.

`test_cases → (A) → Agent 응답 문자열 → (B) → 실제 레이블 리스트 → (C) → 정확도`

### 요구사항

- 각 케이스는 `{"input": str, "expected": ["approved"] | ["denied"]}` 형식이다.
- 케이스마다 서로 다른 `thread_id`를 사용한다.
- 승인·거부 표현이 모두 있으면 문자열에서 더 나중에 등장한 표현을 최종 결론으로 본다.
- 정확도는 정답 수를 전체 케이스 수로 나눈 값이다.

## 정답 3

### 정답 코드

```python
# A: 케이스별 독립 실행
for idx, case in enumerate(test_cases):
    config = {"configurable": {"thread_id": f"eval_{idx}"}}
    result = agent.invoke({"messages": [case["input"]]}, config=config)
    response_text = result["messages"][-1].content

# B: 정규식 매치 위치로 상태 추출
actual = extract_refund_statuses(response_text)

# C: 기대값과 비교 후 누적
if actual == case["expected"]:
    correct_count += 1
accuracy = correct_count / len(test_cases)
```

### 핵심 해설

- Agent 입력은 메시지 딕셔너리, 출력은 누적된 메시지 딕셔너리이며 마지막 메시지의 `content`가 평가 대상 문자열이다.
- B는 자유 형식 자연어를 `list[str]` 레이블로 정규화한다. 기대값도 같은 리스트 형식이어야 직접 비교할 수 있다.
- 평가별 `thread_id` 분리는 이전 사례의 대화가 다음 사례의 판단을 오염시키지 않게 한다.
- 정책 기준이 바뀌면 테스트 데이터의 `expected`와 Agent의 시스템 프롬프트를 함께 수정한다. 표현 형식이 바뀌면 추출 정규식을 수정한다.

## 문제 4. Safety Tool의 검증 순서

### 문제

쿠폰 발급 함수가 정책 위반 요청을 실행 전에 거부하도록 검증 블록을 올바른 순서로 배열하라.

- (가) 주문 상태가 `"배송 지연"`인지 확인
- (나) 실제 쿠폰 발급 성공 결과 반환
- (다) 요청 금액이 20,000원을 초과하는지 확인
- (라) 주문 ID가 데이터베이스에 존재하는지 확인

### 요구사항

- 존재하지 않는 주문의 상태에 접근하여 예외가 발생해서는 안 된다.
- 모든 검증을 통과한 경우에만 실행 결과를 반환한다.
- 각 블록의 입력과 출력 또는 조기 반환 값을 설명한다.

### 정답 코드

```python
def issue_coupon_safe(order_id: str, amount: int) -> str:
    # (다) → (라) → (가) → (나)
    if amount > MAX_COUPON_AMOUNT:
        return "발급 불가: 금액 한도 초과"
    if order_id not in orders_db:
        return "발급 불가: 주문 없음"
    if orders_db[order_id]["status"] != "배송 지연":
        return "발급 불가: 배송 지연 주문이 아님"
    return f"{order_id}의 {amount}원 쿠폰 발급 완료"
```

### 핵심 해설

- 금액 검증은 `int → 통과/거부 문자열`, 존재 검증은 `order_id → 주문 존재 여부`, 상태 검증은 주문 딕셔너리의 `status → 통과/거부 문자열`이다.
- 존재 확인 후에만 `orders_db[order_id]["status"]`에 접근해야 `KeyError`를 막는다.
- 한도 변경은 `MAX_COUPON_AMOUNT`, 허용 상태 변경은 상태 비교 블록, 추가 정책은 성공 반환 전에 새 검증 블록을 수정한다.
- 검증을 LLM의 판단에만 맡기지 않고 실제 부작용을 일으키는 함수 내부에서 강제하는 것이 핵심이다.

## 문제 5. 입력·출력 가드레일 통합

### 문제

다음 보호 계층의 A~C를 채우고 실행 순서를 설명하라.

`user_input → (A) → 허용된 입력 → (B) → 원시 응답 → (C) → 사용자에게 반환`

### 요구사항

- A는 차단 키워드가 포함된 요청을 Agent 실행 전에 종료한다.
- B는 `agent.invoke`이며 입력 메시지와 선택적 `config`를 전달한다.
- C는 민감 키워드와 주민등록번호·카드번호 패턴을 마스킹한다.
- Agent 오류가 사용자에게 예외 상세를 노출하지 않게 한다.

## 정답 5

### 정답 코드

```python
# A = is_harmful_input, B = agent.invoke, C = filter_output
class TrustedAgentExecutor:
    def __init__(self, agent):
        self.agent = agent

    def run(self, user_input: str, config=None) -> str:
        if is_harmful_input(user_input):
            return "해당 요청은 처리할 수 없습니다."
        try:
            result = self.agent.invoke(
                {"messages": [("user", user_input)]},
                config=config,
            )
            raw_output = result["messages"][-1].content
        except Exception:
            return "처리 중 오류가 발생했습니다."
        return filter_output(raw_output)
```

### 핵심 해설

- A는 문자열을 받아 `bool`을 반환하고, `True`이면 B가 전혀 호출되지 않는다.
- B는 메시지 딕셔너리와 `config`를 받아 상태 딕셔너리를 반환한다. 마지막 메시지의 `content`가 C로 전달된다.
- C는 문자열을 받아 마스킹된 문자열을 반환한다. 키워드는 `str.replace`, 번호 형식은 `re.sub`로 처리한다.
- 새로운 공격 표현은 입력 키워드/판별 로직, 새로운 개인정보 형식은 출력 정규식, 대화 분리는 `configurable.thread_id`를 수정한다.
